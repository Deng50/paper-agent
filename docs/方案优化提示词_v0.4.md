## 一、本次讨论的核心结论(2026-05-20 晚)

经领导第二轮评审,v0.3 方案在大方向上 OK,但仍有几处**重要漏洞**和**继续精简的空间**。本次优化必须落地以下转变:

### 1.1 设计哲学进一步深化

| v0.3 仍残留的反模式 | v0.4 正确思路 |
|---|---|
| 让 agent 拿 20 篇候选自己做 for 循环去重 + 评分 | **去重 + 评分封装进 search_papers 工具内部**,agent 拿到的是已处理好的干净结果 |
| 自建 PG `locks` 表做互斥锁 | **删除 locks 表**,完全交给 LangGraph checkpoint + thread_id 机制 |
| 自建 `messages` 表 + 手动写入对话历史 | **删除 messages 表**,LangGraph 自动持久化对话 state,不要 overwrite 它的数据结构 |
| 用"分布式锁"概念保护 profile.md 写入 | **改为原子写**(临时文件 + rename),不是锁,是文件系统语义 |
| 笼统说"agent 自主决策"覆盖所有判断 | **结构化工作交给工具(代码确定性高),agent 只做模糊判断**(挑选 / 推理 / 对话) |
| 方案文档动辄几十页 | **核心方案 3 页内讲清楚**,细节放附录 |

### 1.2 更高层的方法论原则(必须贯彻到每一节)

**A. 大模型不擅长 for 循环**

- agent 做循环时每一轮都要累积全部上下文 → token 浪费 + 幻觉概率上升
- 凡是"逐项处理相同结构数据"的场景,**封装进工具**,工具用代码循环,只把最终结果交给 agent
- agent 的能力用在**模糊判断**(这篇值不值得推、用户的话什么意思),不用在**确定性循环**

**B. 结构化输出靠工具,不靠 prompt 约束**

- "让大模型输出结构化 JSON"靠 prompt 是脆弱的
- 正确做法:**把目标结构定义成工具的输入参数**——大模型输出工具调用,框架自动校验,不符合参数要求时把错误信息打回去重试,**实现校验闭环**

**C. 方案的价值在于"边界清晰",不在于"完美无缺"**

- 任何技术方案都有适用范围和失效场景
- 必须**显式声明**:"本方案在 X 场景下好用,在 Y 场景下会失效,我们接受这个代价"
- 不要追求"覆盖所有 corner case",那会让方案膨胀失控

**D. 区分"重要问题"和"AI 自己想出来的问题"**

- AI 倾向于穷举所有 edge case,然后为每个 case 加一个组件
- 每个问题都要先问:**"不解决会怎样?这个问题我们真的关心吗?"**
- 反例:"用户输入乱码检索不到" → **不解决**,用户乱码就该检索不到,这不是系统的问题

## 二、需要你完成的六项核心改动

### 改动 1:重写文献搜索 + 去重 + 评分逻辑

**当前问题**:v0.3 的 `daily_search.skill.md` 让 agent 自己 for 循环 20 篇做去重和评分,这违反"大模型不擅长 for 循环"原则。

**改动要求**:

1. **search_papers 工具内部封装"搜 + 去重 + 评分"全流程**,agent 调一次就拿到最终干净的 Top N

2. **search_papers 接口设计**:
   ```python
   search_papers(
       queries: list[str],           # agent 生成的检索词(可多条)
       sort: Literal["date_desc"] = "date_desc",  # 强制按日期倒序
       limit_per_query: int = 20,    # 每条 query 召回 20 篇
       dedup_against_memory: bool = True,  # 工具内部自动查重
       min_score: float = 6.0,       # 过滤低分
   ) -> list[Paper]                  # 返回已去重已评分的 Top N
   ```

3. **工具内部流程(由代码确定执行,不是 agent 决策)**:
   - 对每条 query,调 paper-search-mcp,按 `sort_by=date` 拉 Top 20
   - 合并多 query 结果,按 DOI / arxiv_id / normalized_title 去重
   - **查重对照 `./memory/papers/` 所有历史 md 文件**,命中则丢弃
   - 对剩余候选用 Haiku 4.5 单次 prompt **批量评分**(一个 prompt 把所有候选丢进去,不是循环)
   - 按 score 排序返回 Top 5-10

4. **关键约束:必须用 `sort_by=date`(按发表日期倒序)**
   - **失效场景说明**:如果按 relevance 排序,搜索引擎每天返回的都是该领域的经典老论文 → 全被去重过滤 → 系统每天产出 0 篇,直接挂掉
   - 在 PRD 的"假设与边界"章节明确写出这一点

5. **agent 在 daily_search.skill.md 中的角色简化为**:
   - 步骤 1:读 profile.md 了解用户兴趣
   - 步骤 2:生成 3-5 条英文检索词(这是 agent 的模糊判断,不是循环)
   - 步骤 3:**调一次 `search_papers`**,拿到干净结果
   - 步骤 4:agent 用自然语言写推送邮件 + 在对话流呈现
   - 步骤 5:根据 feedback.log 调 update_profile(可选)

6. **删除 v0.3 中的"agent 自己 for 循环查重"环节** —— 标注 ❌

7. **配一张去重子流程图**(≤ 5 节点),清晰画出"工具内部干这件事"

### 改动 2:互斥锁机制 — 删除自建 locks 表

**当前问题**:v0.3 自建 PG `locks` 表替代 Redis,但这是没必要的造轮子。LangGraph 自带 checkpoint + thread_id 隔离机制,本身就解决并发问题。

**改动要求**:

1. **从数据模型中删除 PG `locks` 表** —— 标注 ❌"已删除,改用 LangGraph 内置机制"

2. **互斥逻辑改写为**:
   - 每日推送任务 → 用固定 thread_id `daily_push:YYYY-MM-DD`
   - LangGraph checkpoint 机制保证同 thread_id 不会并发执行
   - APScheduler 11:00 重试时若发现 10:00 任务还在跑,LangGraph 自动拒绝(thread busy)
   - 单用户场景**根本没有真并发**,这套机制 95% 时候是冗余的,但成本是 0

3. **保留的"非锁"机制**:
   - `profile.md` / `feedback.log` 的**原子写**——临时文件 + rename,不是锁,是文件系统语义
   - 实现示例:
     ```python
     def atomic_write(path: Path, content: str):
         tmp = path.with_suffix(path.suffix + ".tmp")
         tmp.write_text(content)
         tmp.replace(path)   # POSIX 原子操作
     ```
   - 在 v0.4 文档中**明确区分"锁"和"原子写"是两个概念**

4. **数据模型章节同步更新**:从 5 张表砍到 4 张(`locks` 删除)

---

### 改动 3:对话历史存储 — 不要 overwrite LangGraph 的 state 机制

**当前问题**:v0.3 设计了 PG `messages` 表 + session md 双写。但 LangGraph 本身自带对话 state 持久化(thread_id → MessagesState),自建 messages 表是 overwrite 它的数据结构,会冲突且痛苦。

**改动要求**:

1. **从数据模型中删除 PG `messages` 表** —— 标注 ❌"已删除,LangGraph 自管对话 state"

2. **明确分层**:

   | 数据 | 谁管 | 怎么读 |
   |---|---|---|
   | 当前对话上下文(thread 内) | LangGraph state(MessagesState) | thread_id 查 |
   | 历史对话归档(跨日 grep) | `./memory/sessions/{date}/{HH-MM}-{trigger}.md` | agent 用 search_memory(scope="sessions") |
   | 业务审计(每日推送任务记录) | PG `pushes` 表 | API 查询 |

3. **session md 写入策略**:
   - **单写**(不是双写):每轮对话完成后,从 LangGraph state 提取最近一轮 user + assistant + tool_calls,**追加到** session md
   - 写入时机:每轮 SSE `done` 事件后触发
   - 这不是 source of truth 双轨,而是**从 LangGraph state 派生出的人类可读 + agent 可 grep 归档**
   - 如果 session md 损坏 → 可从 LangGraph checkpoint(PG 里 LangGraph 自管的表)重建

4. **领导原话精神**:"langgraph 它自己能接管对话持久化,自动建表,它自己定义好数据结构,你不能去给它 overwrite 掉"——v0.4 必须贯彻这一条

5. **session md frontmatter / 正文格式与 v0.3 一致**,保留 `related_papers` / `topics` 等字段供跨日召回

### 改动 5:补充"适用边界与失效场景"章节(PRD 新增)

**改动要求**:

在 PRD 中**新增独立章节**:`§9 适用边界与失效场景`,明确以下内容:

#### 适用场景 ✅
- 用户关注**正在更新的、宽泛的领域**(每天至少有 3-5 篇新文章产出)
- 例:锂电池正负极材料、固态电解质、电池热管理等宽泛大方向
- 每天 Top 20 候选中能挑出 5-10 篇有价值的

#### 失效场景 ❌
- 关注极窄小领域(可能一个月才出 1 篇新文章)
  - 例:"基于图神经网络做硫化物固态电解质界面阻抗预测的特定子方向"
  - 此场景下每天会 0 篇产出,系统对你没价值
- 关注完全静态的历史领域(已基本没有新文献)
- 中文文献(暂不支持,只搜英文)

#### 取舍说明
- **为什么取 Top 20 而不是 Top 100**:20 次循环 token 可控、agent 处理速度快;100 篇大部分会被过滤,白白消耗 API 调用
- **为什么按日期排序不按相关性**:相关性排序会让经典老论文反复占据 Top N → 全被去重过滤 → 系统输出 0 篇
- **为什么不做"中文输入容错"**:用户输入乱码 / 不规范本就不该期待正确结果,系统不该为此付出复杂度代价

| 极窄领域用户无价值 | 低 | [可接受] 在 README 明确告知不适用 |

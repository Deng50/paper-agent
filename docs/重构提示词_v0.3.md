## 一、评审纪要核心结论(2026-05-20)

经领导评审,旧方案(v0.2)被指出存在系统性问题:**过度把每个功能点写成独立 tool / MCP / pipeline 节点,而没有思考"能否用 agent 自身能力 + 文件系统操作实现"**。这是设计哲学的根本错误。

### 1.1 设计哲学的转变

| 旧方案的错误倾向 | 新方案的正确思路 |
|---|---|
| 把每个能力做成独立 tool / MCP / pipeline 节点 | 让 agent 用原生文件系统操作完成,工具数量越少越好 |
| 加路由 / 意图识别层判断"要不要检索" | 检索是 agent loop 里的自主决策——agent 意识到不知道,自己去调工具 |
| 把推送和对话拆成两个 agent | 单 agent 承载所有能力,推送结果就是对话上下文,用户可在下面自然追问 / 重搜 |
| 用向量库 + embedding 做"语义记忆" | 文件系统就是记忆:markdown 文件 + grep + agent 自己读懂语义 |
| 把"如何工作"写死在代码 pipeline 里 | 把"如何工作"写成 SKILL.md 教程,agent 按需阅读 |
| 单租户场景也部署 Redis 做并发控制 | 单租户无并发,Redis 全删,锁迁到 PG locks 表 |

### 1.2 最终架构方案

**单 agent(lit_agent) + 三个核心能力**:
- **搜**:调外部 paper-search-mcp 抓文献
- **读**:用文件系统 grep / cat 读历史文献和历史对话
- **写**:写文献 markdown、写画像、写对话历史

**触发器**(不是 agent 的一部分,是外挂层):
- APScheduler 每天 10:00 给 agent 发系统消息 "hi, 请阅读 daily_search.skill.md 并执行今日推送任务"
- agent 自主按 skill 教程完成搜索、查重、写入、邮件、呈现

**SKILL.md 教程体系**:
- `daily_search.skill.md`:每日推送完整流程
- `memory_recall.skill.md`:历史召回的判断准则
- `profile_update.skill.md`:画像如何自我更新

## 二、需要你完成的四项核心改动

### 改动 1:明确去重与归一化机制

**当前问题**:旧文档只设计了存储,没说清楚去重发生在哪个阶段——是检索时去重还是入库前去重?跨源同一论文(arxiv 预印版 + 期刊正式版)如何归一化也没讲。

**改动要求**:

1. **去重发生在推送(入库)阶段**,而非检索阶段。检索是 agent 主动调用,不存在重复问题。

2. **agent 必须每天重新搜索全部相关领域**,不能因为"昨天搜过类似关键词"就跳过。每天的搜索结果是新一批候选清单。

3. **入库前的去重流程**(写在 `daily_search.skill.md` 里):
   - 对每篇候选,先调 `search_memory(scope="papers")` 用关键词 + DOI 查重
   - 命中**任何历史日期**已推送的同一论文 → 跳过,不再写入
   - 未命中 → 进入评分挑选环节

4. **跨源归一化**(arxiv-2405.01234 vs s2-abc123 实为同一论文):
   - 每篇 paper.md 的 frontmatter 必填 `doi` 字段(若有)
   - `search_memory` 查重时**同时比对 doi 和 normalized_title**(去标点 / 转小写 / 去停用词)
   - 命中任一即视为重复

5. 输出**一张简化的去重流程图**(节点数 ≤ 5,见改动 4 简化要求)

---

### 改动 2:文献记忆的入库与召回机制

**当前问题**:旧文档没说清楚召回触发时机,容易让人想加路由层。**明确禁止任何形式的"意图识别 / 路由判断"层**。

**改动要求**:

#### 入库(agent 自主完成,无独立模块)

- agent 在执行 `daily_search.skill.md` 时,在同一个 loop 里完成"搜 → 查重 → 评分 → 写入文件"
- **禁止**把入库做成独立的 `IngestionPipeline` 或 `DedupModule` 等组件
- 写入即 markdown 文件落盘到 `./memory/papers/{YYYY-MM-DD}/{paper_id}.md`

#### 召回(agent 自主决策何时调,无路由判断)

- **严禁**任何形式的 "if user_query_about_paper then retrieve else skip" 路由代码
- agent 在 loop 中**自主判断**:
  - 用户问"刚才推的第 3 篇" → 上下文有,**直接答**,不调任何工具
  - 用户问"5 天前那篇硫化物论文用什么测试方法" → agent 意识到上下文没有 → **自主调** `search_memory(scope="papers")` → `read_paper`
  - 用户问"上周咱们讨论过哪篇" → 用户记的是对话不是文献 → **自主调** `search_memory(scope="sessions")` → `read_session` 取 `related_papers` → `read_paper`
- 通过 `memory_recall.skill.md` 给 agent 明确的判断准则(用 markdown 表格列出正例 / 反例),**用 prompt 教,不用代码控**

#### 关键设计原则

- **能力来自 agent + skill,不来自工具堆叠**
- 每加一个新 tool 必须自问:"这个能力能否用 agent 读/写/grep 文件实现?"如果能,不加 tool,改写 skill
- 工具数量保持精简(目标 ≤ 10 个),其中外部 MCP 工具占 1-2 个,本地文件工具占 5-7 个

### 改动 3:对话历史以 markdown 文件存储(双写)

**当前问题**:用户 5 天后追问"上周咱们讨论过的那篇硫化物论文,作者是谁?"——只存 PG `messages` 表的话,agent 无法用文件系统操作召回历史对话定位到 paper_id。

**改动要求**:

1. **双写策略**:每轮对话**同时**:
   - INSERT 到 PG `messages` 表(供 API 分页查询,PG 是 source of truth)
   - APPEND 到 `./memory/sessions/{date}/{HH-MM}-{trigger}.md`(供 agent 跨日 grep)

2. **session md 文件命名约定**:
   - 路径:`./memory/sessions/2026-05-20/10-00-daily-push.md`
   - `trigger` 取值:`daily-push` / `chat` / `manual-trigger`
   - 一次连续对话 = 一个文件,每轮 user + assistant + tool_calls 全部完成后一次性 append

3. **session md frontmatter schema**:
   ```yaml
   ---
   session_id: <UUID,与 PG messages.session_id 对应>
   trigger: daily-push | chat | manual-trigger
   started_at: ISO 8601
   last_active_at: ISO 8601
   message_count: <int>
   related_papers:           # 关键字段
     - arxiv-2405.01234
     - s2-abc123
   topics:                   # LLM 自动提取的 2-5 个主题词
     - "硫化物固态电解质"
     - "界面阻抗"
   ---
   ```

4. **正文格式**:每轮按时间序追加 `## HH:MM:SS [role · 可选标注]\n消息内容`

5. **frontmatter 同步规则**:
   - `last_active_at` / `message_count`:每轮更新
   - `related_papers`:agent 调用 `read_paper` 时自动追加该 paper_id(去重)
   - `topics`:每 5 轮触发一次 LLM 提取,只更新增量

6. **search_memory 扩展 scope 参数**:
   - `scope="papers"`:grep `./memory/papers/`
   - `scope="sessions"`:grep `./memory/sessions/`
   - `scope="all"`:两个目录都查

7. **memory_recall.skill.md 中必须明确**:
   - 用户用"上次 / 上周 / 前几天 / 我们聊过"等**模糊时间引用 + 讨论类动词** → 优先 `scope="sessions"`
   - 命中 session md 后读 frontmatter `related_papers` → 拿到 paper_id → `read_paper` 读文献内容
   - 这比直接 grep papers 更准——用户记的是"那次对话",不是"那篇文献的关键词"

8. **故障恢复**:PG 是 source of truth,若 session md 损坏可从 PG `messages` 按 session_id 重建

### 改动 4:所有架构图与流程图大幅简化

**当前问题**:领导原话"复杂,以后能不能画简单点"、"看复杂东西会有厌恶感"。旧文档有 3 张超长 sequence diagram + 多张节点 10+ 的 flowchart,完全违反"图是给人看的"。

**改动要求**:

1. **所有 mermaid 流程图节点数控制在 ≤ 8 个**,只画对决策有意义的步骤

2. **删除所有 sequence diagram**,改成高层 flowchart

3. **必画的几张图**(每张都遵循 ≤ 8 节点):
   - 分层架构图:用户 ↔ agent ↔ skill / tool / memory(4-5 个节点)
   - 部署拓扑:3 个容器 + 几个 volume(≤ 8 个节点)
   - 流程 A 每日推送(≤ 7 节点)
   - 流程 B 用户追问(≤ 6 节点)
   - 流程 C 用户重搜 / 调偏好(≤ 6 节点)
   - 去重子流程(≤ 5 节点)

4. **每张图配一段简短的"要点"说明**,把细节用文字讲清楚,不要把所有内容塞进图

5. **配色规范**(让重点突出):
   - 起点 / 触发器:`fill:#e3f2fd`(浅蓝)
   - agent 决策节点:`fill:#fff9c4`(浅黄)
   - 终点 / 用户感知输出:`fill:#c8e6c9`(浅绿)
   - 文件系统 / 数据:`fill:#e1f5fe`
